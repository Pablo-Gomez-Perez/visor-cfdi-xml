# RF-020 — Clasificación de operaciones

## Objetivo y correspondencia con el Excel

Contabilidad → Clasificación de operaciones. El libro de referencia
06-EGRESOS JUNIO.xlsx, hoja EGRESOS, distingue gastos financieros, costos,
gastos y operaciones mixtas; contiene columnas de IVA exento, 0% y 16%.
RF-020 traslada la decisión administrativa de categoría a la base de datos,
no las fórmulas de IVA ni las determinaciones de pagos. No se publica el
libro ni sus datos.

Una operación documental es el vínculo activo contribuyente_documento de
un CFDI I, E o N. Se permite clasificar ingresos y egresos emitidos o
recibidos; P, T y documentos de retenciones no son objeto de esta
clasificación general en el MVP (no se duplican pagos como erogaciones).
Los cancelados se muestran con el último estado SAT guardado; clasificar
no implica reconocer una operación, asiento, deducción o acreditamiento.

## Flujo funcional

1. Seleccionar titular autorizado. El catálogo es exclusivo de ese titular.
2. Si está vacío, Iniciales crea GASTO, COSTO, GASTO_FINANCIERO, INVERSION,
   INGRESO y OTRA. Repetir no duplica ni altera claves preexistentes.
3. Nueva permite crear clave, nombre y naturaleza; se admiten categorías
   como PAPELERIA, COMBUSTIBLE, HONORARIOS, MIXTA (naturaleza OTRA).
   Activar/desactivar no borra ni cambia asignaciones anteriores; una
   categoría inactiva no puede ser asignada nuevamente. Identidad,
   nombre y naturaleza no son editables en RF-020 para preservar significado.
4. Buscar por mes, año completo o rango de emisión inclusivo, sentido,
   prefijo RFC emisor/receptor y categoría (todas, sin clasificación o
   una concreta, incluidos inactivos). Se muestran documentos activos,
   100 por página, orden SQL por fecha/id descendente. Al ordenar cabeceras
   se ordena solo la página visible; no se promete orden global RF-016 aquí.
5. Seleccionar una o varias filas de la página, elegir categoría y pulsar
   Clasificar. Motivo obligatorio. Retirar registra el paso a sin categoría.
   Si la categoría no cambia, no se añade evento. Los cambios son atómicos.
6. Historial (una fila seleccionada) muestra las categorías resultantes,
   fecha, usuario y motivo en orden inverso, paginado. Ver CFDI abre el
   detalle existente cuando el usuario tiene también ambos permisos CFDI.
7. Cambiar de periodo no modifica las clasificaciones. La misma identidad
   fiscal permanece clasificada mientras cambian los filtros.

## Persistencia

Se reutiliza categoria_operacion (por titular, clave única, naturaleza,
activo). clasificacion_operacion_evento es un historial append-only a
través del servicio: id, contribuyente_id, documento_id, categoria_id
nullable, usuario_id, motivo, creado_en. El último id por vínculo representa
la asignación vigente. Null es retiro explícito; ausencia de eventos
significa no clasificado. Sin columnas duplicadas en documento_fiscal.
FK compuestas impiden categorías ajenas y eventos sin vínculo documental.
No se modifican clasificacion_concepto ni clasificacion_impuesto_concepto:
una categoría general no constituye una distribución de importes. Las
operaciones mixtas pueden etiquetarse para revisión, pero no se distribuye
su importe entre categorías ni se calcula impuesto por tasa. Esto se
reservará para la clasificación detallada de conceptos y tratamientos.

Se serializan las escrituras con bloqueo del vínculo documental y de la
categoría seleccionada; la revisión del listado debe coincidir con el
último evento. En caso de selección obsoleta, categoría inactiva, documento
archivado/ajeno o cualquier error se revierte todo el lote. Máximo 100
documentos por transacción. No se ejecuta SQL/IO en EDT. Los datos del XML
son de solo lectura. El archivado no borra el historial; se recuperará al
restaurar el vínculo. El historial se consulta desde documentos activos.
Altas y estados de categoría se registran en bitacora_evento.
La inmutabilidad del historial es una garantía de la API de la aplicación,
no protección frente a un administrador con acceso SQL directo.

## Instalación

En instalaciones existentes aplicar antes de iniciar esta versión:
`app/database/migrations/20261117_rf020_clasificacion_operaciones.sql`.
Crear respaldo de MySQL antes de DDL. El script crea una tabla si no
existe, sin eliminar ni modificar datos históricos. Instalaciones nuevas
con esquema v1/v2 actualizado ya la incluyen. No reinstalar todo el esquema
sobre una base de trabajo. No se cambia ningún SP.

## Permisos

- OPERACIONES.CONSULTAR: titulares, catálogo, lista e historial.
- OPERACIONES.CLASIFICAR: asignar/reclasificar/retirar, requiere CONSULTAR.
- OPERACIONES.GESTIONAR_CATEGORIAS: alta/estado/iniciales, requiere CONSULTAR.

Se comprueba usuario activo, permisos efectivos y asignación explícita
en cada llamada, incluido ADMIN. El catálogo incremental agrega nuevos
privilegios a ADMIN; los demás roles requieren concesión explícita.
Ver CFDI requiere CFDI.CONSULTAR y CFDI.CONSULTAR_DETALLE.

## Validación

Pruebas JUnit de entradas y construcción Swing sin BD, integración MySQL
8 con migración desde esquema sin tabla, repetición de migración, alta,
idempotencia, historial, retirada, categorías inactivas, documentos
compartidos, rollback, revisión obsoleta, archivado y permisos.
Ejecutar mvn --batch-mode --no-transfer-progress -f app/pom.xml verify.
Validar manualmente WindowBuilder Design para panel y dos diálogos,
resoluciones 740×490 y 900×700, y EXPLAIN ANALYZE con volumen real.
No se declara validación fiscal, contabilización ni determinación de IVA/ISR.
