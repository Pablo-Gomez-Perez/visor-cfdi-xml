# RF-003 — Administración de roles y privilegios

## Objetivo

Permitir que las personas autorizadas administren los roles y configuren
individualmente sus operaciones mediante casillas visibles en la interfaz
Swing. Los privilegios deben tener efecto real **en los servicios** y no
limitarse a ocultar o deshabilitar botones.

El módulo se integra en `Fr_Principal` como `PanelRoles extends JPanel`,
gestionado por el mismo `CardLayout` que Usuarios; no crea otra ventana de
listado. Las ventanas modales son únicamente detalles de rol y la matriz de
privilegios.

## Modelo MySQL utilizado

El SQL canónico es `app/database/schema/visor_cfdi_mysql8_schema_v1.sql`.

| Tabla | Clave | Uso |
| --- | --- | --- |
| `rol` | `id SMALLINT`, `clave UNIQUE`, `descripcion` | Catálogo editable |
| `permiso` | `id SMALLINT`, `recurso`, `accion`, `descripcion` | Catálogo atómico de operaciones |
| `rol_permiso` | PK compuesta `(rol_id, permiso_id)` | Relación configurable de privilegios |
| `usuario_rol` | PK compuesta `(usuario_id, rol_id)` | Roles efectivos de cada cuenta |
| `bitacora_evento` | `id`, `usuario_id`, `entidad`, `entidad_id`, `accion`, `motivo` | Auditoría de modificaciones |

**No se ejecuta DDL.** Hibernate utiliza `hbm2ddl.auto=validate`.
Los registros de `permiso` se insertan idempotentemente al inicio,
utilizando `INSERT IGNORE` y las restricciones únicas del esquema.
Las relaciones `rol_permiso` se administran mediante JPA en transacciones
controladas por Java.

## Catálogo de privilegios funcionales

| Recurso | Acción | Operación protegida |
| --- | --- | --- |
| USUARIOS | CONSULTAR | Abrir y consultar el catálogo de usuarios |
| USUARIOS | CREAR | Registrar usuarios |
| USUARIOS | MODIFICAR | Modificar nombre, login o correo |
| USUARIOS | CAMBIAR_ESTADO | Activar e inactivar cuentas |
| USUARIOS | ASIGNAR_ROL | Asignar roles ordinarios |
| USUARIOS | ASIGNAR_ADMIN | **Privilegio sensible:** asignar ADMIN |
| USUARIOS | RESTABLECER_CLAVE | Restablecer una contraseña de aplicación |
| ROLES | CONSULTAR | Consultar roles |
| ROLES | CREAR | Registrar roles |
| ROLES | MODIFICAR | Cambiar descripción de un rol |
| ROLES | CONFIGURAR_PERMISOS | Asignar y revocar privilegios del rol |
| ROLES | ELIMINAR | Borrar roles personalizados sin usuarios |

No se muestran permisos de módulos CFDI, bancos ni reportes que todavía
no ejecutan reglas de autorización. **Cada nuevo módulo debe añadir sus
operaciones al catálogo y comprobar el privilegio en su servicio antes
de mostrar la casilla.** No debe inventarse funcionalidad futura.

## Política de inicialización y recuperación

- `ADMIN` y `CONSULTA` siguen siendo roles básicos del sistema.
- Si la instalación existente todavía no tiene permisos asignados a
  `ADMIN`, el primer inicio de RF-003 crea el catálogo y le asigna todos
  los privilegios iniciales. De esta forma no se bloquean los
  administradores creados en RF-002.
- `CONSULTA` **no recibe permisos por defecto**. Se pueden asignar
  manualmente con la matriz.
- Los roles personalizados empiezan **sin permisos** (mínimo privilegio).
- Reiniciar la aplicación **no restaura privilegios revocados**. El rol
  `ADMIN` conserva obligatoriamente
  `ROLES.CONFIGURAR_PERMISOS` para poder recuperar otros accesos.
- No se pueden eliminar `ADMIN` ni `CONSULTA`.
- No puede eliminarse ningún rol mientras tenga usuarios asociados.
- La clave de negocio `rol.clave` es inmutable tras el alta; la
  descripción y las asignaciones de permisos sí se editan.
- El usuario debe conservar siempre al menos una cuenta activa con rol
  `ADMIN`, como ya aplica RF-002.

## Controles de seguridad

`AutorizacionService` determina la unión de los permisos de todos los roles
de un **usuario activo**. Cada escritura comprueba permisos efectivos
nuevamente contra MySQL, dentro de su unidad transaccional.

`UsuariosService` deja de utilizar un chequeo genérico del rol ADMIN
para todas las operaciones: comprueba el permiso particular de consultar,
crear, modificar, cambiar estado, asignar rol o restablecer clave.

Asignar el rol `ADMIN` requiere tanto `USUARIOS.ASIGNAR_ROL` como
el permiso sensible `USUARIOS.ASIGNAR_ADMIN`, incluso al dar de alta una
cuenta. El permiso `USUARIOS.CREAR` por sí solo permite altas con el
rol CONSULTA, sin autorizar asignaciones privilegiadas.

Para otros roles, si el operador no dispone de
`ROLES.CONFIGURAR_PERMISOS`, únicamente podrá asignar roles cuyos
privilegios sean un subconjunto de los que él mismo posee. Esto reduce
el riesgo de escalar permisos mediante roles personalizados. La facultad
de configurar permisos se considera una autorización administrativa
superior, y su concesión debe ser extraordinaria.

`RolesService.guardarPermisos` bloquea la fila de rol, valida la lista
completa de IDs, comprueba el privilegio de administración, rechaza la
eliminación de la capacidad de recuperación y sustituye la relación
`rol_permiso`. El commit y el registro en bitácora ocurren en la misma
transacción; los errores provocan rollback.

**Advertencia:** quien tiene `ROLES.CONFIGURAR_PERMISOS` puede conceder
permisos muy poderosos a los roles que controla. Este es un privilegio
administrativo crítico; otorgarlo a otro rol implica confianza equivalente.

**Limitación estructural:** una aplicación Swing conectada directamente a
MySQL no puede imponer RBAC frente a un operador con credenciales de
escritura directas a la base. Para despliegues externos se requiere una
capa de autorización server-side. Los permisos por contribuyente y periodo
son un eje distinto, aún pendiente de implementar.

## UI — patrón Kath ERP

```text
Fr_Principal (JFrame) + JMenuBar + accesos rápidos
  └── panelPrincipalContenedor (CardLayout)
      ├── PanelInicio
      ├── PanelUsuarios
      └── PanelRoles (JPanel, GroupLayout)
          ├── panelEtiquetaRoles
          └── panelCentralContenedor
              ├── panelSuperiorBotones
              │    Crear rol | Modificar | Configurar privilegios | Eliminar
              ├── JTable roles + JScrollPane
              └── panelInferiorBusqueda
                   Buscar | Limpiar | Actualizar
```

`Fr_DatosRol` es un `JDialog` común de alta/edición.
`Fr_PermisosRol` es un `JDialog` de detalle con una `JTable` cuyos
valores `Boolean` se renderizan como **JCheckBox** por cada permiso.
Las columnas incluyen recurso, acción y descripción. Hay botones para
marcar/desmarcar todos, respetando el permiso obligatorio de ADMIN.
Todas las consultas y escrituras de esos formularios usan `SwingWorker`.

La ventana principal abre a 860×600, los catálogos están dentro del área
central, y los diálogos están dimensionados para monitores de alrededor
de 900×700. Se utiliza `GroupLayout` explícito con componentes declarados
como campos y **constructores públicos sin parámetros** para WindowBuilder.

## Comportamiento de privilegios en sesión

La ventana principal recupera permisos efectivos al iniciar y al elegir
**Administración → Administrar usuarios** o **Administración → Roles y permisos**.
La opción **Sesión → Actualizar accesos** permite reflejar los cambios
otorgados por otro administrador sin reiniciar la aplicación.

Los servicios comprueban la autorización en tiempo de ejecución; por ello
una revocación no depende de que la interfaz actualice el estado visual.

## Pruebas y aceptación

```bash
mvn --batch-mode --no-transfer-progress -f app/pom.xml verify
```

Se prueba contra MySQL 8 aislado con Testcontainers:
- Inicialización idempotente sin recrear el esquema.
- Roles personalizados con cero privilegios.
- Creación, modificación, asignación, consulta y eliminación condicionada.
- Revocación con efecto inmediato sobre los servicios de RF-002.
- Rechazo de operaciones administrativas no autorizadas.
- Prohibición de autoasignación de ADMIN sin autorización específica.
- Rechazo de retirar `ROLES.CONFIGURAR_PERMISOS` de ADMIN.
- No restaurar privilegios editados tras reiniciar la inicialización.
- Auditoría en `bitacora_evento`.

### Validación manual obligatoria antes del merge

1. Abrir `Fr_Principal`, `PanelRoles`, `Fr_DatosRol` y
   `Fr_PermisosRol` desde Eclipse WindowBuilder → Design.
2. Verificar que la navegación desde el menú use **CardLayout** y
   no abra un JFrame adicional para el catálogo.
3. Crear un rol y comprobar su presencia en la tabla.
4. Abrir «Configurar privilegios», marcar/desmarcar casillas y guardar.
5. Crear un usuario con el nuevo rol y probar acciones autorizadas y denegadas.
6. Revocar un permiso, usar «Actualizar accesos» y comprobar los cambios.
7. Confirmar que el permiso protegido de ADMIN no puede desmarcarse.
8. Comprobar legibilidad en 900×700 y un ancho cercano a 740 px.
