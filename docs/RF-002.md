# RF-002 — Administración de usuarios

## Objetivo

Disponer de cuentas de acceso propias de Visor CFDI XML, diferentes de las credenciales del motor MySQL. Iniciar el sistema con una única cuenta administradora y permitir el mantenimiento de cuentas de aplicación.

## Esquema SQL utilizado

Se reutilizan sin alterar el esquema v1:

| Entidad | Campos relevantes | Aplicación |
| --- | --- | --- |
| `usuario` | `id`, `nombre_completo`, `login`, `correo`, `hash_contrasena`, `estado`, `creado_en`, `ultimo_acceso` | Identificación y autenticación |
| `rol` | `id`, `clave`, `descripcion` | Roles básicos |
| `usuario_rol` | `usuario_id`, `rol_id` | Asociación usuarios y roles |
| `bitacora_evento` | `usuario_id`, `entidad`, `entidad_id`, `accion`, `ocurrido_en`, `motivo` | Auditoría de administración |

Se crean idempotentemente dos roles `ADMIN` y `CONSULTA` después de establecer la conexión Hibernate; no se almacena una contraseña inicial fija.

## Requerimientos funcionales y criterios de aceptación

| ID | Requerimiento | Criterio de aceptación |
| --- | --- | --- |
| RF-002.01 | Iniciar la capa de persistencia con configuración local y clave MySQL temporal. | Se muestra la ventana de conexión. Un error de esquema o conexión se informa sin intentar DDL. |
| RF-002.02 | Inicializar los roles básicos. | Ejecutarlo dos veces no duplica `ADMIN` o `CONSULTA`. |
| RF-002.03 | Registrar el primer administrador. | Solo cuando no hay usuarios y el rol asignado es ADMIN; una segunda alta inicial se rechaza. |
| RF-002.04 | Autenticar contra la BD. | Credenciales válidas y estado ACTIVO permiten iniciar sesión; las demás se rechazan. |
| RF-002.05 | Registrar usuarios adicionales. | Solo ADMIN puede registrar y asignar ADMIN o CONSULTA. Se respetan las claves únicas. |
| RF-002.06 | Consultar cuentas. | Solo ADMIN puede visualizar lista de usuarios sin contraseñas ni hashes. |
| RF-002.07 | Modificar nombre completo, login y correo, y administrar el estado por operación separada. | Solo ADMIN; login normalizado a minúsculas, entre 3 y 80 caracteres, único en MySQL. Conservar PK y relaciones; cambios con auditoría y rollback. No desactivar al último ADMIN activo. |
| RF-002.08 | Cambiar rol básico. | Solo ADMIN; jamás se elimina el último ADMIN activo. |
| RF-002.09 | Restablecer contraseñas. | Solo ADMIN; se sustituye el hash sin incluir secretos en la bitácora. |

## Seguridad

- Contraseña mínima: 12 caracteres; máximo 128 caracteres.
- PBKDF2-HMAC-SHA256 con sal de 16 bytes, salida de 256 bits, 600 000 iteraciones. Hash almacenado en formato versionado.
- Los datos de entrada de contraseña se limpian de los arreglos `char[]` de los formularios, pero las librerías JDBC requieren temporalmente representaciones de cadena en memoria.
- Las modificaciones usan una nueva comprobación del rol en la BD, dentro de una transacción.
- Un mismo proceso puede abrir más de un formulario; la sesión JPA no es global. Cada operación utiliza su propio `EntityManager`.
- No se debe habilitar `hbm2ddl=update`; solo `validate`.
- No se proporciona autenticación robusta para clientes no confiables con credenciales directas a MySQL. RF-003 y una futura arquitectura cliente/servidor deberán reforzar autorización y políticas de sesiones.

## Revisión manual en Eclipse

1. Abrir `Fr_ConexionMySql`, `Fr_AdministradorInicial`, `Fr_Login`, `Fr_Principal`, `PanelInicio`, `PanelUsuarios` y `Fr_DatosUsuario` desde WindowBuilder.
2. Confirmar que el panel Design renderiza sin excepción y que las propiedades y componentes se pueden seleccionar.
3. Verificar tamaños mínimos y legibilidad en Windows y Linux con FlatLaf.
4. Probar alta del primer administrador sobre base de desarrollo **limpia**, y posteriormente el acceso y el mantenimiento de cuentas.
5. Abrir la tarjeta **Usuarios** desde el menú **Administración**; verificar que no aparece otra ventana de listado. Usar `Fr_DatosUsuario` para crear y editar `nombre_completo`, `login` y `correo`. Confirmar el inicio de sesión con el nuevo login.
6. Intentar asignar a otro usuario un login existente y confirmar que se rechaza sin modificar ningún campo.
7. Corroborar que iniciar sin conexión no congele el formulario y que un error de credenciales nunca muestre su contraseña.

## Modificación de login

El campo `usuario.login` **es editable** en RF-002. Su restricción `UNIQUE` impide duplicados, y las asociaciones de usuarios con otras entidades permanecen enlazadas por `usuario.id`. El servicio valida y normaliza el nombre de acceso antes de iniciar la transacción, comprueba duplicados y registra el login anterior y nuevo en `bitacora_evento.motivo`. Si la operación falla, todos los cambios quedan revertidos.

Una sesión ya iniciada puede mostrar temporalmente el nombre de usuario anterior en la ventana principal; su identidad y autorizaciones continúan asociadas a `usuario.id`. El nuevo login se exige en el siguiente inicio de sesión.

## Límites del módulo

Los permisos granulares (`rol_permiso`, `permiso`), restricciones por contribuyente (`usuario_contribuyente`), periodos y autenticación avanzada se implementarán posteriormente. En RF-002 las funciones de administración se reservan a cuentas con rol `ADMIN`; `CONSULTA` solo accede a la pantalla principal, porque los módulos de consulta CFDI aún no están implementados.

## Homologación de interfaz

El catálogo RF-002 no es un `JFrame`: ahora se muestra en
`com.kathsoft.visor.app.view.usuario.PanelUsuarios`, dentro del `CardLayout`
de `com.kathsoft.visor.app.view.Fr_Principal`. Incluye cabecera de módulo,
acciones superiores, tabla central y filtros inferiores por texto y estado.

Alta y modificación utilizan la misma clase `Fr_DatosUsuario` en un
`JDialog` modal; los formularios anteriores independientes quedaron
retirados. Los botones de cambiar estado, rol y restablecer contraseña
realizan acciones de detalle mediante cuadros modales pequeños, sin abrir
un nuevo catálogo. La interfaz inicial se adapta a pantallas 900×700 y
utiliza `GroupLayout` compatible con WindowBuilder.
