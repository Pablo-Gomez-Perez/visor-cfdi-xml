# RF-004 — Administración de contribuyentes

## Objetivo

Registrar, consultar, modificar y activar/desactivar contribuyentes propios
para mantener su información fiscal separada por titular. El RFC y el nombre
o razón social son obligatorios; CP fiscal y correo de contacto son
opcionales. El catálogo `tercero` es independiente: representar un tercero
de CFDI no le concede el carácter de contribuyente administrado.

Se incorpora la actualización **obligatoria** del catálogo de acciones
RF-003 con cada característica nueva.

## Tablas existentes

La referencia canónica de MySQL 8 es
`app/database/schema/visor_cfdi_mysql8_schema_v1.sql`.

| Tabla | Uso | Modelo Java |
|---|---|---|
| `contribuyente` | RFC único, nombre, CP, correo, estado activo, creación | `ContribuyenteEntity` |
| `contribuyente_regimen` | Vigencias históricas por clave de régimen, sin repetir columnas | `ContribuyenteRegimenEntity` + `ContribuyenteRegimenId` |
| `usuario_contribuyente` | Vinculación explícita de usuarios y contribuyentes | `ContribuyenteEntity.usuariosAutorizados` |
| `permiso` / `rol_permiso` | Privilegios efectivos de operación | `Permisos` + `AutorizacionService` |
| `bitacora_evento` | Trazabilidad de operaciones | `BitacoraEventoEntity` |

No se alteran las tablas ni se ejecuta DDL. Hibernate mantiene
`hibernate.hbm2ddl.auto=validate`.

## Contratos funcionales

| ID | Requisito | Regla de aceptación |
|---|---|---|
| RF-004.01 | Consultar contribuyentes | Requiere `CONTRIBUYENTES.CONSULTAR`; la lista respeta las asignaciones de `usuario_contribuyente`. |
| RF-004.02 | Crear contribuyente | RFC y nombre obligatorios, RFC único, CP/correo opcionales; el creador queda vinculado al registro. |
| RF-004.03 | Editar contribuyente | Requiere `CONTRIBUYENTES.MODIFICAR` y alcance; RFC inmutable, otros campos editables. |
| RF-004.04 | Activar e inactivar | Baja lógica en `activo`; nunca eliminar CFDI/relaciones del contribuyente. |
| RF-004.05 | Historial de regímenes | Agregar periodo, cambiar fecha final y eliminar un periodo erróneo con auditoría; validar intervalos de un mismo régimen. |
| RF-004.06 | Usuarios autorizados | Permiso específico para vincular/desvincular cuentas mediante matriz de casillas y una sola transacción. |
| RF-004.07 | Matriz de roles | Las seis acciones nuevas aparecen en `Fr_PermisosRol` y son revocables/asignables por rol. |
| RF-004.08 | Integración UI | `PanelContribuyentes` es un `JPanel` en `CardLayout`, no otro `JFrame`; detalle reutilizable con pestañas. |

## Matriz de privilegios de RF-004

| Acción estable | Semántica |
|---|---|
| `CONTRIBUYENTES.CONSULTAR` | Ver contribuyentes dentro del alcance autorizado. |
| `CONTRIBUYENTES.CREAR` | Dar de alta un contribuyente. |
| `CONTRIBUYENTES.MODIFICAR` | Cambiar nombre, CP y correo. |
| `CONTRIBUYENTES.CAMBIAR_ESTADO` | Baja lógica o reactivación. |
| `CONTRIBUYENTES.GESTIONAR_REGIMENES` | Alta, actualización y eliminación auditada de vigencias fiscales. |
| `CONTRIBUYENTES.ASIGNAR_USUARIOS` | Gestionar asignaciones usuario/contribuyente y acceder globalmente a contribuyentes. Es un **privilegio elevado**. |

El módulo de acceso por rol permanece editable en el programa.
Las casillas son controles visuales, pero la autorización real se verifica
en `ContribuyentesService` desde la BD para cada operación. La
autorización se compone de:

1. **Permiso del rol**: una operación específica concedida en `rol_permiso`.
2. **Alcance por contribuyente**: el operador debe estar en
   `usuario_contribuyente`; quienes tienen
   `CONTRIBUYENTES.ASIGNAR_USUARIOS` pueden administrarlos globalmente.

Un usuario sin `CONTRIBUYENTES.CONSULTAR` no puede abrir el catálogo desde
la aplicación. Aunque conozca un `contribuyente.id`, los servicios
verifican el alcance antes de devolver el registro o modificarlo.

Las nuevas claves se agregan a la matriz al inicio mediante el
bootstrap idempotente de RF-003. **Sólo al incorporarse por primera vez**
se conceden al rol ADMIN. Si el administrador revoca posteriormente
alguna, reiniciar el programa **no la restaura**.

**Política permanente para cada feat:**
definir privilegios solo para operaciones efectivamente implementadas,
registrarlas en `Permisos`, comprobar cada una en servicios y registrar
su comportamiento en pruebas de permisos/revocación. No basta con
añadir botones o `JMenuItem`.

## Validación fiscal y limitaciones deliberadas

- El RFC se normaliza a mayúsculas y se valida en su **estructura**
  (12 posiciones para persona moral, 13 para física). No se consulta al
  SAT, no se valida la homoclave oficial ni se confirma inscripción,
  vigencia o situación fiscal. No se debe etiquetar como «RFC válido
  ante SAT» después de esta validación.
- El RFC se mantiene **inmutable después del alta** porque es una
  identidad fiscal que será utilizada en CFDI históricos. La corrección
  de identidad, si se necesitara, tendrá un procedimiento especial con
  validaciones y auditoría.
- El CP fiscal acepta exactamente cinco dígitos; no se comprueba todavía
  que sea un código registrado en c_CodigoPostal vigente.
- La clave `clave_regimen` debe contener tres dígitos. **No se comprueba
  actualmente su existencia ni vigencia en c_RegimenFiscal del SAT**.
  Será necesario importar los catálogos oficiales y aplicar reglas de
  compatibilidad antes de utilizar este dato para emitir CFDI.
- Se impiden intervalos de vigencia superpuestos para un mismo código
  de régimen y contribuyente. Pueden coexistir regímenes distintos en
  el mismo periodo, porque una persona puede tributar en varios regímenes.
- Los registros de régimen NO sustituyen los valores preservados en
  los CFDI XML originales. La fecha del CFDI, su timbrado y su periodo
  de efectos fiscales son información independiente.
- Inactivar no elimina físicamente datos ni sus relaciones. La
  importación XML y la conciliación bancaria se implementan después.

## Interfaz gráfica — una sola ventana de detalle

```text
Fr_Principal (JFrame, JMenuBar y accesos rápidos)
└── panelPrincipalContenedor (CardLayout)
    └── PanelContribuyentes extends JPanel
        ├── panelEtiquetaContribuyentes
        └── panelCentralContenedor
            ├── panelSuperiorBotones
            │   ├── Agregar
            │   ├── Detalle / Editar
            │   ├── Activar / inactivar
            │   ├── Regímenes
            │   └── Usuarios autorizados
            ├── JScrollPane + JTable
            └── panelInferiorBusqueda
                └── Buscar + estado + Limpiar + Actualizar

Fr_DatosContribuyente (único JDialog de detalle)
└── JTabbedPane
    ├── Datos fiscales
    ├── PanelRegimenesContribuyente
    └── PanelAccesosContribuyente (Boolean/JCheckBox por usuario)
```

Los tres paneles y el diálogo tienen constructores públicos sin argumentos
sin dependencias de MySQL, de archivos ni del estado de sesión; se usa
`GroupLayout` explícito para que Eclipse WindowBuilder pueda editarlos.

El detalle abre a aproximadamente 755×555 px, dentro de una pantalla
de 900×700; la ventana principal conserva 860×600. Las operaciones de
persistencia se ejecutan en `SwingWorker`.

Los botones de acceso rápido y de menú se habilitan con permisos
actualizados; al elegir el módulo, `Fr_Principal` vuelve a consultar
los permisos mediante `SwingWorker`.

## Transacciones y verificaciones

- Hibernate/JPA se utiliza para operaciones CRUD habituales. No se
  incorporan procedimientos almacenados artificialmente porque el
  tamaño del catálogo no requiere procesamiento masivo.
- Las operaciones que modifican varias tablas agrupan relaciones y
  auditoría en una sola transacción de Java.
- Se utilizan bloqueos de contribuyente para cambios de vigencias y
  asignaciones concurrentes.
- Las pruebas en MySQL 8.0.46 con Testcontainers cargan el SQL completo
  del repositorio en un contenedor aislado.
- Las pruebas comprueban unicidad RFC, actualización/baja, permisos,
  revocación, aislamiento de contribuyentes, historial de regímenes,
  rollback y conservación de auditoría.

## Revisión manual requerida antes del merge

1. Abrir `Fr_Principal`, `PanelContribuyentes`,
   `Fr_DatosContribuyente`, `PanelRegimenesContribuyente` y
   `PanelAccesosContribuyente` desde Eclipse WindowBuilder → Design.
2. Comprobar creación, edición (RFC no editable) y reactivación.
3. Comprobar regímenes con fechas, validación de solapamientos y eliminación.
4. Comprobar matriz de usuarios vinculados por contribuyente.
5. Revocar en RF-003 cada acción y confirmar restricciones reales.
6. Probar navegación y legibilidad en 900×700 y en la ventana mínima.
7. Confirmar que no se crean JFrames de listado independientes.

**Límite transversal:** al conectarse Swing directamente a MySQL,
la autorización Java no protege frente a clientes no confiables con
credenciales directas de escritura a la BD. Para producción distribuida
se necesitará un servicio de autorización server-side.
